# Internationalization (i18n)

There are two independent language systems in this project. It is important not to confuse them:

| System               | What it controls                                                            | Where it lives                                |
| -------------------- | --------------------------------------------------------------------------- | --------------------------------------------- |
| **UI language**      | The language of interface labels, buttons, error messages                   | `client/src/i18n/` + `client/src/locales/`    |
| **Content language** | Which locale of a plugin entity's localized fields is displayed             | `useLanguages()` hook + (your `getLocalized()` util) |

## SDK Usage Boundary

`@staffbase/plugins-client-sdk` is used for two things:

1. **Content language** — `getBranchLanguages()` and `getBranchDefaultLanguage()` inside `useLanguages()`.
2. **Instance URL** — `useInstanceUrl()` to build links into the Staffbase instance (e.g. profile links). Use this only on end-user-facing pages; admin components should read `useAuth().staffbaseUrl` from the JWT-injected `window.__USER__` instead.

Nothing else in this codebase calls the SDK.

UI language is resolved from `window.__USER__.locale` (set by the server from the Staffbase JWT) so end-user facing pages render in the same language the user has configured in Staffbase. When no Staffbase context is available (e.g. standalone access without a JWT), i18next falls back to the browser's `navigator.language`.

## UI Language (i18next)

### Setup

Initialized in [`client/src/i18n/init.ts`](../../client/src/i18n/init.ts) before React mounts. Translation files are loaded lazily via Vite's `import.meta.glob`.

**Supported UI languages:** `de`, `en`, `es`, `fr`, `pl`

**Namespaces:**

| Namespace   | File                          | Used by                                                |
| ----------- | ----------------------------- | ------------------------------------------------------ |
| `template`  | `locales/{lang}/template.json`| All user-facing UI (EndUserView placeholder, error boundary, session expired) |
| `admin`     | `locales/{lang}/admin.json`   | Admin panel — settings, audit log, items demo (tabs, category, sort, items-list, item-form, changelog) |

### Hooks

```ts
const { t } = useI18n();       // namespace: "template"
const { t } = useAdminI18n();  // namespace: "admin"
```

End-user facing pages (`EndUserView`) call `i18next.changeLanguage()` in a `useEffect` on mount, switching to the Staffbase user locale from `window.__USER__.locale`. This scopes the language override to user-facing routes only — navigating to the admin panel reverts to the browser language.

## Content Language

When you add plugin-specific entities with localized fields (e.g. `name: jsonb` keyed by locale), use the `useLanguages()` hook to expose the branch's supported content locales and the current user's chosen locale. Build a `getLocalized(jsonbField, currentLanguage, defaultLanguage)` helper that resolves to the right string with fallbacks.

The template ships no localized entities yet — the helper is yours to add when you introduce the first one. The demo `items` table uses a single `name: text` column (not a localized `jsonb`) for simplicity; if your domain needs per-locale field values, follow the launchpad pattern: `name: jsonb` keyed by locale, plus a `getLocalized()` helper that picks the right key based on `useLanguages().currentLanguage`.

---

## Content Locale Format

Staffbase uses underscored locales (`en_US`, `de_DE`, `fr_FR`, …) for content. i18next uses short codes (`en`, `de`, `fr`, …) for UI. The two systems are kept independent — never use one as a substitute for the other.

## Adding a New UI Language

1. Create `client/src/locales/{lang}/template.json` and `admin.json`, copying all keys from the English files.
2. Translate the values.
3. Add the short code to the `supportedLngs` array in `client/src/i18n/init.ts`.
4. (Optional) Add the language to per-customer override slots under `client/public/customers/{slug}/locales/{lang}/`.

---

## Per-Customer UI Language Overrides

```
client/public/customers/{slug}/locales/
├── en/
│   ├── template.json    ← override user-facing keys
│   └── admin.json       ← override admin keys
├── de/
│   ├── template.json
│   └── admin.json
└── …
```

Only the keys present in an override file are changed; missing keys fall through to the base files in `client/src/locales/`. The `{slug}` is the JWT `branch_slug` claim (or `LOCALDEV_BRANCH_SLUG` in dev). The `_default` slot is reserved for the no-override baseline.

**New languages** — adding a language in an override file does not automatically make it available in the i18next `supportedLngs` list. To support a previously unsupported language for a specific customer, add it to `supportedLngs` in `init.ts` first, and ensure corresponding `locales/{lang}/template.json` and `admin.json` base files exist.

## Testing i18n

The MSW test setup in [`client/src/__tests__/setup.ts`](../../client/src/__tests__/setup.ts) configures i18next in **key mode**, where `t("placeholder.user-title")` returns the literal key. This makes tests robust against translation changes — assert against keys, not human-readable strings.

The per-customer override merge mechanism is exercised by [`client/src/i18n/__tests__/customer-overrides.test.ts`](../../client/src/i18n/__tests__/customer-overrides.test.ts).

## Admin namespace shape

`admin.json` is organised into stable top-level sections so future plugins can drop the items demo and keep the rest:

| Section            | Used by                                                        | Safe to delete with items demo? |
| ------------------ | -------------------------------------------------------------- | -------------------------------- |
| `title`, `settings-btn`, `placeholder.*` | StudioHeader title + Settings button + admin placeholder | No                              |
| `tabs.*`, `status-tabs-aria`, `add-item-btn`, `search-items`, `search-cancel`, `item-count_*` | Items SegmentedControl + search + count |  Yes                             |
| `category.*`, `category-filter-*`        | Filter dropdown                              | Yes                              |
| `sort.*`                                 | Sort Select                                  | Yes (if your domain has no sort) |
| `items-list.*`, `item-form.*`            | Items table + create/edit dialog             | Yes                              |
| `settings.*`                             | SettingsDialog (API token, danger zone)      | No                              |
| `changelog.*`                            | ChangelogDialog (audit log)                  | No                              |
| `user-deleted`, `user-unknown`           | Changelog rendering                          | No                              |
| `localizations.*`                        | `LocalizationsActions` studio component      | No (keep until you remove the component) |
